# 分鏡與節奏

Reels 是被滑過去的。前 3 秒決定會不會看完，之後每一幕都要讓人來得及讀完、
又不會等到想滑走。這份講怎麼切幕、每幕停多久、大標怎麼寫。

## 骨架

技術主題預設用這條線，範本（css-subgrid）就是照它排的：

| 幕       | 秒數  | 畫面                                       | 大標在做什麼                         |
| -------- | ----- | ------------------------------------------ | ------------------------------------ |
| 痛點     | 0–3   | 壞掉的樣子 + ✗ 標出哪裡壞                  | 用觀眾遇過的狀況問一句               |
| 原因     | 3–7   | 同一個畫面 + 原本的寫法                    | 一句話講為什麼會這樣                 |
| 中間步驟 | 7–15  | 大家會先想到的解法：修好一半 ✓、還壞一半 ✗ | 「改用 X 呢？」→「但 Y 還是歪的」    |
| 解法     | 15–17 | 真正解法的程式碼，重點行亮起               | 點名解法，講它補上了中間步驟缺的那塊 |
| 結果     | 17–22 | 切成修好的樣子 + ✓（配樂在這裡 drop）      | 講看到了什麼                         |
| 原理     | 22–27 | 在畫面上標出機制 + 2～3 張說明卡片         | 一句話的心智模型                     |
| 第二例   | 27–37 | 換一個情境重複「壞 → 程式碼 → 修好」       | 「再舉一例」，點出跟第一例的差別     |
| 支援度   | 37–42 | 瀏覽器版本 / 可用性                        | 能不能用                             |
| 結尾     | 42–45 | 一行總結的程式碼 + 貼文同款 CTA            | 收藏／分享                           |

- **痛點一定要有畫面**，不是只有字。觀眾要在第 1 秒就認出「這我遇過」。
- **不要從原本的寫法直接跳到答案。** 範本一開始是 flex → subgrid，使用者看了轉不過來：
  觀眾腦中的下一步是「那改用 grid 呢？」，影片跳過它，答案就像憑空冒出來。
  先演那個直覺的解法，讓它修好一半（按鈕對齊了）、留下一半（內文還是歪的），
  真正的解法才有「補上缺的那塊」的理由。中間步驟跟真正解法要用**同一個示範畫面**，
  差異才看得出來。
- 「原因」可以跟「解法」併成一幕，但「結果」不能省：修好的那一刻是整支片的高潮，
  配樂的 drop 跟 ✓ 都落在這裡。
- 第二個例子要換**維度**或**情境**（範本是 rows → columns、卡片 → 表單），
  不要是同一件事換個顏色。沒有夠不同的第二例就不要硬湊，整支縮到 25～30 秒。
- 支援度一幕只在「新功能能不能用」是問題時才放；老語法不需要。

總長 25～45 秒，取 2.5 的倍數（配樂一小節）。

## 每幕停多久

**大標在畫面上至少 2.5 秒，每多 1 個字加 0.15 秒。** 副標另外算。
程式碼區塊一行至少 0.5 秒，而且整塊一起出現 —— 逐行打字的效果看起來很酷，
但最後一行打完就要切幕了，觀眾根本來不及讀（使用者實際回饋過）。

- 程式碼的重點行在出現後 **0.9 秒**內亮起：先讓眼睛找到整塊的位置，再告訴它看哪裡。
- 同一個示範畫面跨好幾幕（痛點 → 原因 → 解法）時，示範區留著不動，只換大標和下方的
  程式碼。每幕都整個換掉，觀眾每 4 秒就要重新認一次畫面。
- 轉場固定 0.5 秒（`tl.show` 預設），退場比下一幕進場早 0.2 秒開始。
  所有東西都同時進場很吵：同一幕裡錯開 0.12～0.35 秒一個一個出來。

## 視線：一次只給一個地方看

Reels 大多是靜音滑的，觀眾沒有旁白告訴他看哪裡，畫面同時有三處在變就會全部錯過
（Redis 淘汰策略那支的第一版：程式碼放在示範區下面，使用者回饋「不會注意到下面有 allkeys-random」）。

- **關鍵字放在動作發生的地方。** 會影響示範結果的設定（策略名、屬性值）直接做進示範面板裡，
  換設定時只翻那一格；不要放在下面另一塊程式碼區塊等觀眾自己對照。
- **聚焦：沒輪到的區塊調暗到 30%。** 把示範拆成幾個可以各自亮暗的區塊（指令、設定、狀態、資料），
  每一步只亮正在變的那塊。用一張 `[秒, 亮哪幾塊]` 的表排，不要散在各處手寫透明度
  （做法見 `src/reels/redis-shared/panel.tsx` 的 `FocusAt`）。
- **用一個會移動的東西帶路。** 要講因果（請求 → 找不到 → 回資料庫）時，讓同一個元素沿路走過去，
  不要讓幾個框同時跳出來。眼睛會跟著動的東西走。

## 大標怎麼寫

- **最多 2 行，一行 11 個中文字**（80px，寬 935.84）。超過就是這句話太長，不是版面太小。
- 副標 1 行、23 字內，補大標沒說完的那半句；大標自己夠清楚就不放。
- 用觀眾的話，不用規格書的話：「按鈕怎麼總是對不齊？」而不是「巢狀格線的軌道對齊問題」。
- `**粗體**` 一句最多一處，標的是那句話的轉折（對不齊、各自排版、借用）。
- 大標裡的技術名詞（解法的名字）用 `**粗體**`，在 `tone="ok"` 的幕會是萊姆綠；
  `` `code` `` chip 留給說明卡片這種小字，放在 80px 大標裡太搶。
- 不要 emoji 塞在大標裡：Noto Sans TC 沒有 emoji，會掉到系統字型，基線跟大小都對不上。
  ✓ ✗ 這類記號用 `.mark` 畫。

## 示範畫面怎麼做

- **示範要是真的。** 用真的 CSS 排出壞掉與修好的兩種版面，對齊線從 DOM 量出來畫。
  畫假圖的話，觀眾照著程式碼寫會得到不一樣的結果。
- 內容要故意長短不一，問題才看得出來（範本三張卡片的標題是 1 行、2 行、1 行，
  表單 label 是 2、6、4 個字）。長度剛好差不多的話，壞掉的版本看起來也沒壞。
- 字級在手機上要讀得到：示範區內文 ≥ 26px、按鈕 ≥ 26px、程式碼 30px。
- 需要標出「機制」時（例如 grid 的 row 軌道），把示範區整塊縮小位移騰出空間放標籤，
  不要把標籤疊在內容上。

## 交給使用者確認的分鏡

寫 code 之前先給這張表：

```
| 秒數 | 大標 | 副標 | 畫面 |
| 0–3  | 卡片裡的按鈕／怎麼總是**對不齊**？（tone=bad） | — | 三張卡片，按鈕高度不同，✗ 標出 |
| ...  |
```

加上總長、`drop` 落在哪一秒、第二例是什麼。使用者改完再開始排時間軸。
